**新事实（探测得出）**：同一份文件，走不同 URL 的缓存行为不一样——

| URL | 结果 |
|---|---|
| `/?sharecode=…`（根） | 长期 HIT 旧副本，`Age` 每 2 秒重置仍在命中，多次重发不清 |
| `/index.html?sharecode=…`（文件路径） | **跟随文件 mtime 更新**，读到新版 |
| `/?sharecode=…&v=x` | 换 URL 必然 MISS，拿到新版 |

所以根路径那条缓存被"钉死"了，而文件路径这条是正常静态缓存（按 mtime 失效）。

**方案（两层）**：
1. **对外链接改用文件路径**：`https://fanuc-milling-w.app.workbuddy.host/index.html?sharecode=OTD3JQJQPI` —— 链接永久不变，发布后自动跟更新。
2. **页面自带版本自检**：加载后 30 分钟一次 `fetch('version.json?ts=…', {cache:'no-store'})`，与 `APP_VERSION` 不一致就在右下角弹「线上已更新到 vX · 刷新到新版」，点击用 `?_=<时间戳>` 跳转（换 URL 绕开缓存）。这样即使某个节点缓存顽固，用户也能一键自愈。

配套：`tools/release.js` 发版时自动写 `version.json`（`{v, built}`）并纳入提交；断言 194 → **195**（无 location 环境下自检不报错）。

## 已完成：彻底解决「每版换链接」（v1.6.2，架构调整）

用户不接受 `&v=` 每版换链接。目标改为：**一个永久链接，发布后自动跟更新**。

**探测出关键事实**：同一份文件，不同 URL 的缓存行为不同 ——

| URL | 行为 |
|---|---|
| `/?sharecode=…`（根） | 长期 HIT 旧副本，`Age` 每 2 秒重置仍在命中，重发不清 |
| `/index.html?sharecode=…` | 跟随文件 mtime，但**这次发布后仍停在上一版**（说明它不是可靠通道） |
| `/app.html?sharecode=…`（全新路径） | 全新路径无历史缓存，MISS → 立即拿到新版 |

结论：**缓存是「按完整 URL 钉住」的**，任何"曾经用过的 URL"都可能在某个时间点卡住。所以不能靠"找个好 URL"，要让**会变的东西不在被分发的那个 URL 上**。

**最终架构**：

```
index.html  (1 KB, 永不变)  →  location.replace('app.html' + location.search)
app.html    (~940 KB, 每版变) ← 所有内容都在这里
version.json  {"v":"1.6.2","built":…} ← 应用用来做版本自检
```

- 对外固定链接：`https://fanuc-milling-w.app.workbuddy.host/app.html?sharecode=OTD3JQJQPI`
- 入口那 1 KB 就算被缓存旧了也无害——它本来就只做转发，且永远不需要改
- 应用加载后 30 分钟一次 `fetch('version.json?ts=…')`，版本不一致就弹「线上已更新到 vX · 刷新到新版」，点击用 `?_=<时间戳>` 跳转（换 URL 绕开任何残留缓存）

**实测（全新浏览器配置）**：
- `/app.html?sharecode=…` → 徽标 **v1.6.2**，无提示条，0 异常
- `/?sharecode=…`（根）→ 仍是 v1.5.0（根缓存还没刷，但已不影响分发链接）
- 提示条实测：`position:fixed`、底部居中、文案「线上已更新到 v9.9.9 当前页面是 v1.6.2 的缓存副本 [刷新到新版] ×」，跳转 URL 正确拼出 `&_=<时间戳>`

**工具链改动**：`tests/`、`sync-doc`、`version`、`release`、`shoot-panel` 全部改指向 `app.html`；`release.js` 每次发版写 `version.json`；`make-qrcode.py` 传根链接时自动改写成 `/app.html?sharecode=…` 并停止追加 `&v=`。断言 195 全过。

## 已完成：图纸转 SVG 落地（v1.7.0 → v1.7.2）

用户决定：**SVG 作为唯一入口；点列直出准确率太低，删掉；DXF 暂不做。**

**新链路**：`图片 →（模型）图元 JSON →（本地）合成 SVG →（既有链路）轮廓 → 程序`

- `dwgRasterToPrims`：模型只输出 line / arc（圆心+R+起止角）/ circle，并引标注原文
- `dwgPrimsToSvg`：端点贪心串接（顺序随意）、接缝焊接、生成单条连续子路径
- 三道校验：**S01 闭合**（缺口多少 mm、第几段）、**S02 自交**、**S03 尺寸一致**（R/Ø/角度不参与外形比对）
- 界面：图元清单（每条长度/圆心/R/起止角）+ 标注原文对照 + 下载 SVG；S01/S02 阻断生成
- 删除：点列的 `dwgRasterToIR` / `dwgNormalizeRaster` 整条路径

**上线后实测（T3-1）**：

| 版本 | 结果 |
|---|---|
| v1.7.0 | 90 秒后「不是有效 JSON」——提示词太长导致模型输出夹解释 |
| v1.7.1 | 100 秒，16 个 arc 全部解析出来，但**端点差 0.1~0.5mm 被拆成 16 条独立子路径**（16 条轮廓，1 外 15 内），尺寸 78.517×78.517 |
| v1.7.2 | 5 秒，模型这次只给 7 个图元且**有 4 处接缝超过 1mm（最大 116mm）**，被 **S01 阻断**，界面明说"模型给的图元端点对不上" |

**这轮修掉的真问题**（都是实测暴露）：

1. SVG 路径必须是**单条连续子路径**——每段各写一个 `M` 会让每段变成"两点退化轮廓"被 `parseSvgIR` 丢弃；
2. 圆弧包围盒要取 **0/90/180/270 极值点**，靠采样会得到 20×9.997 这种数；
3. **接缝 1mm 内自动焊上**（告警），超过断开并阻断——否则 16 段弧会变成 16 条轮廓；
4. R / Ø / 角度类标注不能参与"外形尺寸"比对，否则 R100 天天误报；
5. 提示词压缩 + 超时 120s + 失败时回报模型原文开头（定位"话太多"还是"被截断"）。

**结论**：管道本身对了（图元能解析、校验能拦住坏数据），但**模型对这类波浪形轮廓的几何输出不稳定**：三次请求给了三套不同的图元，接缝对不上。当前 S01 会把它们全部挡住——不会产生错程序，但也出不来程序。

## 实测两张用户图（v1.7.2 → v1.7.3）

**图1**：纯轮廓示意图（波浪形闭合轮廓 + 刀具偏移虚线 + A/B/C/D 四个基点标记），**无任何尺寸标注**。

| 版本 | 结果 |
|---|---|
| v1.7.2 | 35 秒，4 段 R60 弧、闭合 0.013mm、90.5×80，程序 **221 行**，但 **192 个 G01、0 个圆弧** |
| v1.7.3 | 33 秒，8 段弧（R12.5 外凸 + R10 内凹交替）、闭合、40×40，程序 **59 行**（G02 15 + G03 9 + G01 6） |

**图2**：纯文字坐标表 A(-50.00,-53.02) B(-38.65,-27.52) C(-12.57,-32.66) D(-22.90,-35.53)。

| 版本 | 结果 |
|---|---|
| v1.7.2 | 3 秒，报「图片为纯黑」——**假原因**：透明底 PNG 转 JPEG 时透明像素变黑 |
| v1.7.3 | 2 秒，正确报「图中仅为四组二维坐标点的文字列表，缺少零件轮廓…无法解析几何图元」 |

**这一轮修的两件事**：

1. **透明底 PNG 补白**：canvas 先 `fillRect` 白底再 `drawImage`。剪贴板截图常带 alpha，不补白整张图变黑，模型直接拒识——之前被误判成「模型不认文字图」。
2  **折线 → 圆弧拟合**（`dwgFitCircle` Kasa 代数拟合 + `dwgFitArcs` 贪心扩窗，误差 ≤0.02mm）：`irToNC` 现在输出 `G02/G03 … I… J…`。同一张图 221 行 → 59 行，192 个 G01 → 6 个。

**关键结论**：图1 没有任何尺寸标注，模型只能给"形状对、尺寸猜"（它自己说 40×40，按图面比例应是 90×80 量级）。图2 恰好就是这张图的真实基点坐标——**两张图合起来才构成一个完整零件**。这正好证明「基点坐标录入」这条路的必要性：有坐标就该按坐标建模，而不是让模型猜比例。

## 已完成：A + C（图元可编辑 / 基点建模）v1.8.0 → v1.8.3

**A 图元可编辑**：图元清单每项都是输入框（直线 X1/Y1/X2/Y2；圆弧 圆心/R/起止角；孔 X/Y/R），
「应用修改并重新合成」→ 重跑 S01/S02/S03。两者共用 `dwgRecompose()`。

**踩的四个坑**（全部实测暴露）：

1. `dwgPointsToPrims` 产出原始格式，`dwgRecompose` 又套了一层 `dwgPrimToRaw` → 全部图元被当垃圾丢掉，报「没有可用图元」。`dwgPrimToRaw` 加 `p.type` 分支。
2. 只改半径时圆心不跟着变 → 端点漂移 → 轮廓开口被 S01 拦。改成「保两端点、重算圆心」。
3. 上面这个分支还是不生效：输入框只显示两位小数，用 1e-9 比较永远判定"圆心也改了"。改用 0.005 容差。
4. **已知限制**：`irToNC` 先在顶部顶点处旋转轮廓再做圆弧拟合，如果整条轮廓只有一段弧且正好被起点切开，两半都凑不够 5 个点 → 退化回全 G01（几何仍正确，只是行数多）。图1 那种多弧轮廓不受影响（G02 15 + G03 9）。

## 已完成：断口不补线，抬刀 G00 跨越（v1.9.0）

用户反馈「所转程序只按线条走，断的地方直接 G00 跳刀」，确认后选择「抬到安全高度再 G00，不补线」。

**改动**：

1. `dwgPrimsToSvg`：断口处**不再连直线**（原来 ≤1mm 会被"焊"上，等于替用户补线改了零件形状），
   一律另起子路径，并额外返回 `fragments`（按断口切好的采样段）与 `origin`。
2. `dwgOpenIR()`：开放段**直接造 IR**（每段 `open:true`），不再走 `parseSvgIR` ——
   因为后者会把"零高度/零宽度"的退化形状（单段直线）丢掉。
3. `irToNC`：开放段不写闭合回程，引刀沿首段反方向、退刀沿末段正方向各延长 `刀半径+2mm`；
   每段之前一律 `G00 Z安全高度` → `G00 X Y` → `G01 Z切深`。
4. 注释加 `OPEN`：`(CONTOUR 1 OUTER OPEN PASS 1/3 Z-1)`；S01 从"阻断"改为"提示"，界面列出每个缺口的位置与大小。

**实测（线上 v1.9.0，60×40 方框右边缺 3mm）**：

```
G00 Z10
G00 X-7 Y0
G01 Z-1 F176
G41 D01 X0 Y0 F439
G01 X60 Y0
G01 X60 Y37        ← 走到断口
G40 X60 Y44        ← 沿末段方向退刀
(CONTOUR 1 OUTER OPEN PASS 2/3 Z-2)
G00 Z10            ← 下一层之前先抬刀
```

**踩的坑**：`irToNC` 重排轮廓时 new 了一个对象，把 `open` 字段丢了 → 开放段仍按闭合处理，补出一段回程线。必须在 map 里显式透传。
